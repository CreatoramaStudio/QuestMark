# Godot benchmark: notes

**STATUS (2026-11-06): all measured logic is now a C++ GDExtension (godot-cpp, class `QuestBench`); the full SPEC protocol was re-run on it.** The earlier GDScript implementation (`legacy/main.gd`) and its full-run results (`results/gdscript-old/`) are kept for the comparison. The sections after "C++ port" describe the GDScript version (history); where they say `main.gd` or GDScript, read `src/quest_bench.cpp` for the current code. Rule behind the port: performance-critical Godot code is C++ (godot-cpp), never GDScript.

## C++ port (GDExtension)
Files: `src/quest_bench.{h,cpp}` (the whole benchmark, one `Node3D` subclass), `src/register_types.{h,cpp}`, `CMakeLists.txt`, `bench.gdextension`, `main.tscn` (root node is type `QuestBench`, no script; if the extension is missing the scene fails to load, so a leftover GDScript cannot run silently), `legacy/main.gd` + `legacy/main_gd.tscn` (old GDScript, excluded from the export by `exclude_filter="legacy/*"`), `../tools/build-godot-ext.sh`.

Behaviour, CLI options (`--scenario --mode --run --warmup --measure --out --diag-busy-ms`, plus the E and F options in the section "Scenarios E and F"; `--headless` is an engine flag as before), CSV columns, `.summary.txt`, `.env.txt`, scenario layouts, seed 12345 `RandomNumberGenerator` call order, default damping 0.1, the `physics_ms` stopwatch definition and the awake counting follow the sections below unchanged. The C++ calls the same public Godot APIs as the GDScript did: `RigidBody3D`/`StaticBody3D`/`PinJoint3D` nodes, `PhysicsDirectSpaceState3D::intersect_ray` with one reused `PhysicsRayQueryParameters3D` (still one `Dictionary` result per call; no batching API), `PhysicsServer3D::body_get_state(BODY_STATE_SLEEPING)`, `MeshInstance3D` with Box/Sphere/CapsuleMesh in render mode.

Build (Windows x86_64, MSVC or clang-cl through the Visual Studio generator; no scons; the editor is only needed for the API dump):
1. godot-cpp checkout (shallow clone of github.com/godotengine/godot-cpp). It has branches 4.4, 4.5 and master only (no 4.7 branch or tag on 2026-11-06), so master was used (commit `b472519c42be09c1acec3fd63acd4010fc586ad4`, which also ships `extension_api-4-7.json`). No git submodules are needed.
2. Dump the API of the installed editor: `$GODOT_EXE --headless --dump-extension-api --dump-gdextension-interface` from a scratch folder; the `extension_api.json` (Godot 4.7.2 mono) is passed as `GODOTCPP_CUSTOM_API_FILE`, so the bindings match the editor. godot-cpp master reads its interface description from its own `gdextension_interface.json`; the dumped `gdextension_interface.h` is not used by the CMake build.
3. godot-cpp's binding generator is Python. The dev machine has no Python (only the Microsoft Store stub), so the build used the `python.exe` bundled with another installed application (Python 3.13, standard library only, nothing installed or downloaded); pass it as `PYTHON3`.
4. `GODOTCPP_DIR=<godot-cpp> GODOT_API_JSON=<extension_api.json> [PYTHON3=<python3>] tools/build-godot-ext.sh [template_debug|template_release|all]`. Output: `godot/bin/<compiler>/libquestbench.windows.<target>.x86_64.dll` (gitignored; `COMPILER=msvc|clang`, see the section "Render fix, clang build, Jolt limit check"). template_release uses the Release configuration (MSVC MaxSpeed = `/O2`, `NDEBUG`, static CRT, checked in the generated vcxproj), template_debug the Debug configuration. Build trees go to `<project>/.tmp/godotext-build/<compiler>/`. The release build took about 1.7 minutes with 0 warnings.
5. `$GODOT_EXE --headless --path benchmark/godot --import` once (creates `.godot/extension_list.cfg`), then `--export-release "Windows Desktop" <outdir>/QuestBench.exe`. The exporter packs `bench.gdextension` into the pck and copies the release DLL next to the exe by itself (the only preset change was `exclude_filter="legacy/*"`). The `windows.release.x86_64` entry of `bench.gdextension` selects the template_release DLL; editor runs and debug exports use the template_debug DLL. The env file says which one ran (`bench_extension: ... template_release build`).

What changed in the measurement code:
- GDScript interpretation overhead of the ray loop, the per-tick code and the awake counting is gone; those run as native code calling the same engine APIs. The summary labels for `awake_count_cost_ms` and `script_physics_process_ms` now say "native".
- `gc*` columns stay 0; the summary line reads `total_gc_pause_ms: 0 (native C++ GDExtension, no GC)` (merge-results.pl still parses it).
- C++ evaluates function arguments in unspecified order, so every group of RNG draws (jitter x, y, z; position, axis, angle; ray origin, direction) is sequenced explicitly in the order GDScript evaluated them. Evidence that the sequence is the same: the measured-window ray hit totals match the GDScript runs (raycast-1000: 201768 in all 3 new and all 3 old runs; raycast-10000: 1961233 in 3 of 3 new and 2 of 3 old runs, the third old run is 1959600 and is also the one old run with 1200 instead of 1201 rows; mixed: 437095 new vs 437096 to 437098 old, expected to differ slightly because the bodies move).
- Time source is still `Time::get_ticks_usec()`; frame rows are kept in memory and written at the end.
- `physics_ms` has the same definition (end of `QuestBench::_physics_process` to start of `QuestBench::_process`, summed per frame). The engine now reaches `_ready/_process/_physics_process` through GDExtension virtual calls instead of the GDScript VM; that call path is engine-side and not measured separately.
- No unavoidable behavioural difference was found. Remaining differences against Stride are in SPEC.md and the sections below (RNG sequences, ceiling body, `physics_ms` boundaries, damping formulas, restitution).

## Scenarios E (`unlock`) and F (`scale`) in the C++ extension (2026-11-06)
CLI (args after `--`, all written with `=`; `--warmup 2` with a space is silently ignored):
- `--scenario=unlock-render-mixed` (forces mode render, `Engine.max_fps = 0`, vsync off, window 1280x720; physics still ticks every 1/60 s of wall time), `--scenario=unlock-physics-mixed`, `--scenario=unlock-physics-pit-2000` (both force the unpaced physics loop below).
- `--scenario=scale --bodies=N --mode=physics|render [--unpaced=1]` (`--unpaced=1` forces physics mode and gives the `scale-unlock-physics` variant). Bodies are Scenario A's (alternating box/sphere, same RNG call order, 12 x 12 columns, 0.6 spacing, layers from y = 1); the pit interior is `max(22, ceil(22 * sqrt(N / 2000)))` m (22, 22, 32, 44, 63, 88, 125 m for N = 1000 ... 64000), floor interior + 2, walls 6 m high. N = 2000 equals pit-2000.
- Output files: `<out>/godot-jolt-<label>-<mode>-<run>.csv` (+ `.csv.summary.txt`, `.env.txt`) with label = the scenario name for E (modes `render` / `physics`: `godot-jolt-unlock-physics-mixed-physics-1.csv`) and `scale-<N>` for F with mode `physics`, `render` or `unlock-physics` (`godot-jolt-scale-16000-unlock-physics-1.csv`). CSV columns unchanged.
- Launch: unpaced runs (E physics variants and `--unpaced=1`) must run WITHOUT `--headless` (see below); the paced scale-physics run keeps `--headless` as before.
- New summary lines (all scenarios): `measured_s`, `fps` (frames / measured s), `steps_per_s` (physics ticks counted in `_physics_process` / measured s), `ticks_counted` with the engine's `physics_frames` delta over the same window (cross-check), `paced_frames` (frames, 60 Hz x measured_s, ratio), `physics_delta_s` (min and max `delta` seen by `_physics_process`; proves the simulated step is 1/60 s), `pacing`, `wall_ms, tick frames only`, `wall_ms` and `physics_ms (tick frames)` for `first_5s` and `last_5s` of the measured window (frames by cumulative wall time; the two overlap when measure < 10 s), `awake_bodies_at_end` (counted at exit), `bodies_outside_pit_at_end` (pit scenarios; |x| or |z| beyond the interior half-width, or y < -0.5), `working_set_mb` (process working set at the end, Win32 `K32GetProcessMemoryInfo`, with the peak), `bodies`. The env file adds the Jolt limits, `max_physics_steps_per_frame`, `time_scale`, `unpaced`. `--diag-tps=<n>` (default 60000) is a diagnostic override of the unpaced tick rate; never use it for results.

Unpaced physics method (proved by counts, not assumed): Godot passes `physics_step * time_scale` to the physics step and `time_scale` does not change the tick rate (tried first: `time_scale = 1000` alone gave 60 ticks/s with huge steps, and all bodies left the pit). The working setup is `physics_ticks_per_second = 60000`, `time_scale = 1000` (step stays 1/60 s), `max_physics_steps_per_frame = 1`, `max_fps = 0`, so every frame owes a tick and runs exactly one, back to back. The engine's own main loop is used (no custom stepping). Proof per run: `physics_delta_s min = max = 0.016666667`, `ticks_counted` equals the engine `physics_frames` delta, and ticks == frames. Limits and gotchas found by measurement:
- A minimized window made the loop sleep about 6.9 ms per frame (145 fps cap, also under `--headless`), and `--headless` alone has the same 145 fps floor even with 10 bodies (wall median 6.90 ms; `--diag-tps` 600 / 6000 / 60000 all gave 144.9 fps). So unpaced runs are not minimized, need a real window (no `--headless`), and switch the render loop off (`RenderingServer.render_loop_enabled = false`) so nothing is drawn; frame overhead then is about 6 us at 10 bodies (127 k fps). A blank window is visible during the run.
- Because a window and the Vulkan device exist, the working set of unpaced runs includes about 290 MB of graphics overhead (N = 1000: 392 MB unpaced windowed vs 103 MB paced headless): compare memory between N values within one variant only.
- `awake_bodies` in unpaced runs is refreshed every 30th frame (every frame ticks, and counting costs about 0.3 ms per 3000 bodies); `steps_per_s` also includes our per-tick code (the 1000 rays of mixed, about 0.8 ms) and the engine's tick-start sync, so it is a loop rate, not 1000 / `physics_ms`.
- The sim runs several times faster than real time, so a 20 s wall window covers 27 to 170 simulated seconds for N <= 4000 and only 3 to 5 simulated seconds for N >= 16000 (the pile is still forming, see `first_5s` vs `last_5s`).
- CSV `physics_ms` is per frame (sum over the frame's ticks). In paced runs that fall behind (N >= 4000 in 60 Hz mode) Godot catches up with up to 8 ticks per frame, so a row can hold several steps; read `ticks_counted` vs frames.
- SUPERSEDED 2026-11-06: per-scenario limits set by the extension, see "Scenario G ... and the Jolt limits change" below.
- Jolt limits had to be raised in `project.godot` (all scenarios, the file is shared): `max_bodies` 10240 -> 70000, `max_body_pairs` 65536 -> 1048576, `max_contact_constraints` 20480 -> 1048576 (capacity caps, not tuning; the default `max_bodies` would refuse bodies beyond 10240). Checked later (see "Jolt limit regression check"): the larger pair and constraint limits raise `physics_ms` of A to D by about 20 percent (pit-2000 3.43 -> 4.14 ms, mixed 2.94 -> 3.51 ms); `max_bodies` alone does not.
- Warm-up: with the default 5 s paced warm-up, scale N = 4000 paced physics measured a first-5-s `physics_ms` median of 133 ms (impact of the falling pile; the paced run lags real time) and 666 of 1200 expected frames; the same stage with `--warmup=8 --measure=5` gave `physics_ms` median 7.95 ms, p99 wall 19.08 ms and 300 of 300 frames. Warm-up must cover the fall (about sqrt(2h/g) of simulated time: 1.9 s at N = 4000, 3.7 s at 16000), which a lagging paced run does not reach in 5 s of wall time. Hypothesis, not tested: the same applies at 8000 and above.

## Render fix, clang build, Jolt limit check (2026-11-06)
Scope of every number below: this one machine, Godot 4.7.2 stable mono release export, short runs (10 s measured after the stated warm-up, 3 runs per cell, one process at a time, A/B alternated ABAB), physics mode headless. The raw CSVs were scratch (runs `r1` first A/B, `r2` mixed rerun, `r3` and `r4` limits) and were deleted after the numbers were taken; the quoted values are the per-run medians read from them.

### 1. Render fix (render mode only; physics mode creates no meshes)
A render check had shown the raycast scenes drawing nothing and the other scenes missing floor, walls and ceiling (the old deviation 6 below: only dynamic bodies had meshes). Now, in render mode only: `_build_raycast_statics()` adds a `MeshInstance3D` to each of the 2000 statics with the shared box / capsule / sphere mesh chosen by the same `i % 3` as the shape; `_static_box()` (floor, walls, chains ceiling, scale-pit) adds a `MeshInstance3D` using ONE shared 1 m `BoxMesh` (`unit_box_mesh`) scaled by the node to the box size (same idea as Stride's shared unit box model scaled per entity); `_add_camera_and_light()` adds a `WorldEnvironment` with a cornflower-blue background colour (0.392, 0.584, 0.929) and colour ambient light (white, energy 0.5), still one directional light. Proof: window screenshots of the exported release build (client area captured from outside the process with a small PowerShell helper, 1280 x 720, pit-2000, raycast-1000, mixed, viewed): pit-2000 shows floor and the four walls (inner wall sides grey, not black), raycast-1000 shows the 2000 boxes, capsules and spheres on the blue background, mixed shows pit, ceiling slab, chain links and bodies. Limit: the pit-2000 and mixed cameras (unchanged) look over the near wall from low, so most bodies are hidden behind it; body visibility was checked in raycast-1000 and as small bodies in mixed. No render-mode timing was re-measured after this change (the render-mode numbers in the tables above were taken without the static meshes and are not comparable to new render runs).

### 2. clang build (LLVM clang-cl 20.1.8)
- `tools/build-godot-ext.sh` has `COMPILER=msvc|clang` (script default msvc; the default build used for export and results is clang, see below). Output goes to `bin/msvc/` or `bin/clang/` (`libquestbench.windows.<target>.x86_64.dll`), build trees to `.tmp/godotext-build/<compiler>/<target>`. `SELECT_DEFAULT=1` rewrites `bench.gdextension` to the built compiler's folder (committed state: `bin/clang/`); the exporter copies the selected release DLL next to the exe (flat, by file name).
- What worked: the Visual Studio 17 2022 generator with `-T ClangCL` (the ClangCL platform toolset exists), but the toolset looks for a VS-bundled LLVM 19 that is not installed (`MSB8073`). The script therefore sets the MSBuild properties `LLVMInstallDir` (from the clang-cl on PATH) and `LLVMToolsVersion` (its major version, 20); then `clang-cl` and `lld-link` of the standalone LLVM are used. The Ninja bundled in VS's CMake folder was not needed. The clang build prints many `-Wunused-parameter` warnings from godot-cpp's generated headers (not our code) and took about 8 minutes (MSVC about 2 minutes, built in parallel with it).
- Same settings (read from the generated vcxproj of both trees): godot-cpp commit `b472519c`, same extension API json, Release `Optimization=MaxSpeed` (= `/O2`), `NDEBUG`, `RuntimeLibrary=MultiThreaded` (static CRT), C++17. No clang-specific flags were added.
- Proof the clang DLL is clang's: the DLL embeds `clang version 20.1.8` through `__clang_version__`, and the env file line `bench_extension_compiler:` (new) prints it (clang runs: `clang 20.1.8 (clang-cl, MSVC-compatible driver)`; MSVC runs: `MSVC cl 194435229 (_MSC_VER 1944)`). `llvm-readobj --file-headers`: MSVC DLL linker version 14.44, SizeOfCode 274432, SizeOfImage 475136, file 437248 bytes; clang DLL linker version 14.0 (lld-link default), SizeOfCode 314368, SizeOfImage 593920, file 512000 bytes. The exported DLL is byte-identical to `bin/clang/` (`cmp`). `dumpbin` printed nothing outside a VS developer shell, so `llvm-readobj` was used.

### Scenario G implementation (`src/quest_bench.cpp`: `_build_debris_world`, `_spawn_event`, `_despawn_due`, `_make_piece`)
- CLI: `--scenario=debris|debris-pooled --rate=R --mode=physics|render` (R may be fractional; `--warmup` defaults to 10 s for G, `--measure` 20 s). Files: `godot-jolt-debris-<R>-<mode>-<run>.csv` and `godot-jolt-debris-pooled-<R>-<mode>-<run>.csv` (+ `.summary.txt`, `.env.txt`), same token rule as the Stride side. CSV: the 9 standard columns, then `event_ms,despawn_ms,debris_live` at the end (G files only).
- World: pit 22 x 22 interior (`_build_pit`), 25 static blocks 2 x 2 x 2 (`StaticBody3D`, 5 x 5 grid, spacing 3, centre y = 1). Block order: seeded Fisher-Yates permutation of the 25 (seed 12345), reshuffled after each 25 events.
- Event k is due at simulated time k / R s (first at t = 0; simulated time = physics ticks completed / 60 when written; at 200 Hz it is ticks / 200, SPEC "Scenario G"), inside `_physics_process` before the step. If the slot's block is intact it is removed (`remove_child` + `memdelete`), else nothing is removed. Then 64 pieces (4 x 4 x 4, edge 0.5, mass 0.125, shared box shape and physics material, default damping 0.1, friction 0.5) are created (`memnew` RigidBody3D + CollisionShape3D, `add_child`) at the old block's cell positions, each with `apply_central_impulse(radial_unit * 1.5 * mass * (1 + f))`, f seeded uniform in [-0.2, 0.2], and a seeded angular velocity uniform in [-3, 3] rad/s per axis (SPEC gives no spin magnitude). Orientation is identity. RNG call order per piece: f, then spin x, y, z.
- Lifetime: the pieces of an event are removed (`remove_child` + `memdelete`) in the first tick where simulated time >= event time + 8 s, all pieces of the event in the same frame, before that tick's events. The block of a slot is rebuilt (new `StaticBody3D`) when the last live event of that slot is removed; the rebuild is inside `despawn_ms`. This is the rule of the Stride side (SPEC's literal rule cannot hold above R about 3: 25 blocks, 8 s lifetime). The summary line `events_completed` splits events on an intact block from events on an already-used block (smoke R=8: 25 vs 78 of 103).
- `event_ms` = stopwatch around block removal + creation of the 64 pieces + impulses, summed over the ticks of the frame, 0 on frames without an event; `despawn_ms` the same for removals + block rebuild; `debris_live` = pieces alive after the frame's ticks. Godot can run up to 8 ticks per frame when it lags, so one row can hold several events. The stopwatch ends before the engine's step: the work Jolt does for the new bodies lands in `physics_ms` of the following tick.
- `debris-pooled`: same semantics as the Stride side (parked bodies stay in the simulation). `ceil(R * 8) + 2` events' worth of pieces (64 each) are created at start, added to the tree and put to sleep at y = -1000 (1 m grid, `set_sleeping(true)`); an event takes 64, teleports them (`set_transform`), wakes them (`set_sleeping(false)`) and applies the same impulse and spin; removal zeroes both velocities, teleports back to the parking cell and sleeps. No `memnew`, `memdelete`, `add_child` or `remove_child` per piece in the event. The pool grows on demand (`pool: ... misses` in the summary). Awake count and `debris_live` count live pieces only (parked ones are excluded).
- Render mode: one `MeshInstance3D` per piece with ONE shared 0.5 `BoxMesh` resource (blocks and the pit use the shared unit box scaled); no per-piece mesh or material creation. Render mode is uncapped, as in the other scenarios.
- Summary lines added for G: `debris_variant`, `debris_rate_events_per_s`, stats of `event_ms` over event frames and `despawn_ms` over removal frames, `wall_ms` stats on event frames, removal frames and non-event frames, `debris_live` max and mean, `awake_bodies` min and max, `events_completed`, `pool`, `impulse_probe` (speed of one piece right after the impulse call and at the next tick). `working_set_mb`, `bodies_outside_pit_at_end` and `awake_bodies_at_end` use the live pieces.

## Column meaning (proved by the experiments below)
- `wall_ms`: time between `_process` calls.
- `physics_ms`: OWN STOPWATCH, not `Performance.TIME_PHYSICS_PROCESS`. It is the time from the end of this script's last `_physics_process` in a frame to the start of that frame's `_process`, summed over the frame's ticks (second and later ticks in the same frame add the gap before their `_physics_process`). It covers Godot's `end_sync` + the Jolt step, and excludes our script and the ray batch. Source-read in the fork's `main/main.cpp` (about line 4991): per tick the order is `PhysicsServer3D::sync()`, `flush_queries()` (node syncs for every active RigidBody3D), `_physics_process`, step, `iteration_end`. Definition 2 (tick mark, default): the first tick of a frame also includes its tick start (`sync()` + `flush_queries()`), stamped by the do-nothing `QuestTickMark` XR interface whose `_process()` runs once per frame before the tick loop; the tick-start window is also written to the CSV column `tick_start_ms`. `--tick-mark=0` gives definition 1 (first tick's tick start outside the stopwatch); result sets without `physics_ms_def: 2` in env.txt are definition 1. It is 0 on frames without a physics tick (render mode: most frames). The summary also prints "tick frames only" stats; use those for render mode.
- `query_ms`: `Time.get_ticks_usec` around the ray loop, last tick's value held on frames without a tick. Includes GDScript call overhead and a Dictionary allocation per call.
- `awake_bodies`: number of dynamic bodies whose `PhysicsServer3D.body_get_state(rid, BODY_STATE_SLEEPING)` is false, recomputed on tick frames only (about 0.25 ms of script per tick for 2000 bodies, `awake_count_cost_ms` in the summary; it lengthens the frame but sits inside the 16.7 ms pacing slack in physics mode). Statics are not counted; raycast scenarios report 0 because they have no dynamic bodies.
- `gc*`: 0 (GDScript).
- The summary also prints the engine monitor `TIME_PHYSICS_PROCESS` (updated about once a second, includes script time) and our script's `_physics_process` time, for cross-checking only.

## API choices
- Physics engine: `physics/3d/physics_engine="Jolt Physics"` in project.godot; the env file of every smoke run printed `backend: Jolt Physics`.
- Bodies: `RigidBody3D` (mass 1, default sleeping, CCD off), `StaticBody3D`; shapes `BoxShape3D`, `SphereShape3D`, `CapsuleShape3D`; one shared `PhysicsMaterial` (friction 0.5, bounce 0.1). Shape resources are shared between bodies.
- Rays: `PhysicsDirectSpaceState3D.intersect_ray` with one reused `PhysicsRayQueryParameters3D`, called in `_physics_process`, pre-generated seeded ray set. No batching API used.
- Joints: `PinJoint3D`, defaults (no limits), `exclude_nodes_from_collision` left at its default.
- Statistics: percentiles by nearest rank on sorted values. First-120 max is over the first 120 recorded (post-warm-up) frames, not process start.

## Deviations and interpretations
1. Capsule: Godot `CapsuleShape3D.height` is total height including the caps, so height 0.5, radius 0.15 means a 0.2 cylinder part. SPEC is ambiguous; the Stride side may use cylinder length 0.5.
2. Chains: 10 joints per chain (ceiling to link 0, then 9 link-link) = 1000 joints; SPEC.md was changed from 900 to 1000 for this reason. Ceiling bar is one static slab 11 x 0.2 x 11 (bottom at y = 12). Link centers at y = 11.75 - 0.5*i; joint anchors at y = 12 - 0.5*i.
3. Impulse: "every 10th link" interpreted as the 10th (bottom) link of each chain, (2,0,0) via `apply_central_impulse`, applied in the first `_physics_process` call.
4. Mixed: pit interior 32 x 32 (floor 34 x 34); chains as in C; 2000 A bodies on a 0.6 grid in columns within +-9 m excluding |x|<6 and |z|<6 (chain area), layers from y = 1. 1000 rays (volume 40 x 20 x 40) are cast against the world (A bodies, chains, pit walls); B's 2000 static shapes are NOT added in mixed. SPEC does not define this.
5. Pit grid for A (plain pit-2000): 12 x 12 columns x layers from y = 1 until 2000 bodies (14th layer partial), 0.6 spacing, jitter +-0.05 per axis; changed from 10 x 10 x 20 to match Stride and the SPEC rule (re-exported 2026-11-06, smoke: 2000 bodies, awake_bodies max 2000). Bodies alternate box/sphere by index.
6. Physics mode: window minimized via `DisplayServer.window_set_mode`, no meshes/camera/light, `Engine.max_fps = 60`. Render mode: `max_fps = 0`, vsync disabled in code and project; frames outnumber physics ticks (about 790 fps vs 60 ticks in the smoke run), so `query_ms` and `awake_bodies` hold the last tick's value and `physics_ms` is 0 on frames without a tick. Only dynamic bodies got meshes in the GDScript version (default material); that was fixed in the C++ extension (statics and environment now drawn, see "Render fix").
7. Random directions are normalized cube samples (not uniform on the sphere). Godot's RNG sequence will not equal Stride's even with seed 12345.
8. Frame rows are buffered in memory and written at the end.
9. Not tuned: solver iterations, sleeping, `physics_jitter_fix` (0.5), `max_physics_steps_per_frame` (8), default damping. Godot's default linear and angular damp is 0.1 (`physics/3d/default_linear_damp`, `default_angular_damp`), which is not zero; the Stride side should match or note the difference. Jolt limits at their defaults: `limits/max_bodies` 10240, `max_body_pairs` 65536, `max_contact_constraints` 20480 (not checked whether the 2000 to 3000 body scenes hit the pair/constraint caps; hypothesis only).
10. Real Jolt setting names (proved by listing `ProjectSettings.get_property_list()` in 4.7.2): `physics/jolt_physics_3d/simulation/velocity_steps` = 10, `position_steps` = 2, `allow_sleep` = true, `sleep_velocity_threshold` = 0.03, `sleep_time_threshold` = 0.5. The earlier guesses were correct. `physics/3d/solver/solver_iterations` (16) and `physics/3d/sleep_threshold_*` exist but belong to Godot's own physics engine; their effect under Jolt is not tested. All of these are written to the env file.
11. GDScript is interpreted: the ray loop includes per-call script overhead and a Dictionary allocation per call, so `query_ms` mixes script and engine cost.
12. Renderer: project default (`forward_plus` printed in the env file; Vulkan Forward+ in the render smoke run). Steam Deck/Proton may need Compatibility or Vulkan notes.

## Verified by real runs (Godot 4.7.2 stable mono, dev machine, smoke lengths only)
1. `--headless --path benchmark/godot --import` ran with no error or warning on project.godot or main.tscn, and main.gd parsed; no fix to project.godot was needed. Needed code changes: the physics_ms and awake_bodies replacements below, plus the new diagnostics.
2. All five scenarios ran to completion in physics mode headless (`--warmup=1 --measure=3`): 180 or 181 rows each (about 60 frames/s, as expected for 3 s), no NaN or inf in the CSVs, `awake_bodies` non-zero where dynamic bodies exist. Pit-2000 also ran in render mode (not headless, 2386 rows) and in physics mode with a real (minimized) window (180 frames, wall median 16.67 ms).
3. Headless 60 Hz pacing: with `Engine.max_fps = 60` and vsync off, headless wall_ms median was 16.64 to 16.67 ms in every physics-mode smoke run; one tick per frame (pit-2000: 1 frame of 180 without a tick). Minimized real window: same (p99 16.98 ms). Window minimization did not throttle the loop in those runs. Limit: 3 s windows, one machine.
4. `Performance.TIME_PHYSICS_PROCESS` is not usable for `physics_ms`:
   - Experiment (chains, 8 s measured, headless, `--diag-busy-ms`): with 0 ms busy-wait the engine monitor median was 1.76 ms and the stopwatch 0.69 ms; with an 8 ms busy-wait inside `_physics_process` the monitor median was 10.24 ms (+8.48) while the stopwatch was 0.75 ms. So the monitor INCLUDES the script's `_physics_process` time (plus some per-tick engine work outside the step), and the stopwatch isolates the step.
   - Raycast-10000, 8 s: monitor median 11.44 ms, own script time about 9.7 ms, step stopwatch 0.02 ms (static bodies only). The monitor therefore includes the ray batch.
   - The monitor changed only 4 times in the 3 s of the first pit-2000 smoke CSV (about once a second), so it is useless per frame.
5. `PHYSICS_3D_ACTIVE_OBJECTS` does NOT work under Jolt in 4.7.2: it read 0 on every row of the first pit/chains/mixed smoke runs (those scenes certainly had awake bodies). Replaced by the `PhysicsServer3D.body_get_state(..., BODY_STATE_SLEEPING)` count; it is live (pit-2000 over a 15 s headless run: 2000 at start, 1932 near the end).
6. Impulse on the first tick works under Jolt: a free `RigidBody3D` (gravity off, damping 0) given `apply_central_impulse((2,0,0))` in the first `_physics_process` read velocity (0,0,0) right after the call and (2,0,0) on tick 2, x = 0.0333 after tick 2 (scratch experiment). In chains, `PinJoint3D` with `node_a`/`node_b` set after `add_child` bound all 1000 joints (1000 joint nodes; max deviation of link spacing from 0.5 was 0.0017 m up to tick 600), and the bottom link of chain 0 moved from x = -4.5 to -4.05 (tick 30) and -4.62 (tick 600).
7. Chains stay awake: `awake_bodies` was 1000 on every sampled row of a 15 s headless chains run (every 3 s), consistent with SPEC. Pit-2000 had not settled to sleep by 15 s (about 1930 awake); the cause (for example rolling spheres) is a hypothesis, not checked.
