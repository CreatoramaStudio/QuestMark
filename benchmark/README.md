# QuestMark engine benchmark

Purpose: measure Godot (Jolt, optionally a PhysX fork) and Stride (Bepu) and ezEngine (Jolt) on the same physics-heavy scenes (A to G), so the engine choice in `docs/engine-choice.md` can rest on numbers. The rules are in [SPEC.md](SPEC.md); this file only says where things are and how to run them. Status: the full protocol (A to G, both profiles) ran at 200 Hz on 2026-11-07 for Godot Jolt, the Godot PhysX fork and Stride Bepu (JIT and AOT). A reduced second run on 2026-11-08 re-measured Godot Jolt, ran PhysX at 97bc4de for stages A and C, and ran ezEngine Jolt for all stages. Both runs used one desktop machine. The results are not committed; the analysis and the provisional verdict are in `docs/engine-choice.md` section 12.2. A third, partial run on 2026-11-08 compared the Godot body APIs (nodes against PhysicsServer3D RIDs + MultiMesh) for Jolt and the PhysX fork (section 12.3). Nothing has run on a Steam Deck, and none is available (godot and stride NOTES, "not done" lists).

## Layout
- `godot/`: Godot project; the measured logic is a C++ GDExtension in `src/` (godot-cpp), `legacy/` holds the old GDScript. Notes: [godot/NOTES.md](godot/NOTES.md). PhysX fork port: [godot/PHYSX.md](godot/PHYSX.md), patch in `godot/patches/`.
- `stride/`: Stride 4.4.1 + Bepu solution (C#, .NET 10, scenes in code). Notes: [stride/NOTES.md](stride/NOTES.md). `render-smoke.ps1` is the render check.
- `ezengine/`: ezEngine (Jolt plugin) C++ application and project, built from an ezEngine checkout (`.tmp/ezengine`). Status: timed in the 2026-11-07/08 runs (raw path, "direct Jolt") and in a full A to G run through the engine components (flavour `components` at that time, now the default path, docs/engine-choice.md 12.6). Notes and open items: [ezengine/NOTES.md](ezengine/NOTES.md).
- `tools/`: `build-godot-ext.sh`, `export-godot-fork.sh`, `build-ezengine.sh`, `run-all.sh`, `merge-results.pl`, `parity_check.pl`, `build-progress.sh` (scons fork builds), `ext-build-progress.sh` (extension build), `bench-progress.sh` (benchmark run). Paths given to the tools may be relative to the project root.
- `results/`: output (CSV, `.summary.txt`, `.env.txt`, `SUMMARY.md`); `results/gdscript-old/` is the old GDScript run. Not ignored by git yet (see SPEC "Layout").
- Scratch files go in `.tmp/` at the project root only.

## Build
Only release builds give valid results; editor and debug runs do not.
- Godot extension: `GODOTCPP_DIR=<godot-cpp> GODOT_API_JSON=<extension_api.json> [PYTHON3=<python3>] COMPILER=clang|msvc bash tools/build-godot-ext.sh [template_debug|template_release|all]`. `GODOT_API_JSON` comes from `<godot exe> --headless --dump-extension-api`. Output: `godot/bin/<compiler>/`. Script default is msvc; the committed `bench.gdextension` selects `bin/clang/` (`SELECT_DEFAULT=1` rewrites it). Then export the "Windows Desktop" preset with the editor and matching export templates (godot NOTES, "C++ port", step 5).
  Progress: `bash tools/ext-build-progress.sh clang template_release watch` (compiled units / units in the vcxproj files, then "linked"). After the project folder moved, the script removes the stale CMake tree and rebuilds (clang about 14 min on the dev machine, 1092 units).
- Stride JIT: `dotnet build -c Release` in `stride/` (SPEC label `bepu`).
- Stride Native AOT: `dotnet publish -c Release -r win-x64 -p:BenchAot=true -o <dir>` (label `bepu_aot`). `IlcInstructionSet` is `avx2` in `stride/StrideBench.csproj` for this variant, so the exe needs a CPU with AVX2. The ILC link step needs `vswhere.exe` on `PATH` (the Visual Studio Installer folder; stride NOTES, "Native AOT variant").
- One-command path: `bash benchmark/tools/setup.sh` (downloads, compiles, exports; see the Quick start in the top README) and `bash benchmark/tools/run-benchmark.sh [--quick|--full]`; `QuestMark.bat` wraps both. The optional PhysX fork build is `bash benchmark/tools/setup-physx.sh` (PhysX SDK via `tools/physx/build-physx-sdk.bat`, fork, extension); its full build was not run end to end.
- Godot PhysX fork: build the fork and the PhysX SDK as in [godot/PHYSX.md](godot/PHYSX.md), then `FORK_TEMPLATE=<fork template_release exe> FORK_EDITOR=<fork editor console exe> bash tools/export-godot-fork.sh [label]`. Optional `GODOT_EXT_DLL`, `EXPORT_ROOT` (default `.tmp/export-fork`). Output: `<EXPORT_ROOT>/<label>/QuestBench.exe`.
- ezEngine: `[WORKSPACE=qm-bench] [CONFIG=Dev] bash tools/build-ezengine.sh` (CMake workspace inside the ezEngine checkout, `EZENGINE_DIR` default `.tmp/ezengine`; output printed at the end). Measured runs use `CONFIG=Shipping`, Dev is for smoke tests. Render mode needs a one-time asset transform, see [ezengine/NOTES.md](ezengine/NOTES.md).

## Run
- Variants (one `run-all.sh` invocation each, strictly sequential): Godot Jolt (`BENCH_ENGINE=jolt`), Godot PhysX fork (`BENCH_ENGINE=physx` with `BENCH_FLAVOUR`), Stride Bepu JIT (`STRIDE_FLAVOR=bepu`), Stride Bepu Native AOT (`STRIDE_FLAVOR=bepu_aot`). GodotPhysics3D is not benchmarked.
- Planned runtime from `--dry-run` (stages ABCDEFG): about 57 to 58 min per variant, 138 runs (range 40 to 80 min); about 3 h 50 min for all four. The ladder capacities in the estimate are assumptions; setup and retries are not included.
- Set the exe paths and `OUT_DIR` in a gitignored local file (for example the `env` block of `.claude/settings.local.json`), never in tracked files. Re-export the Godot exe after any change to `benchmark/godot/src` or `project.godot`, and rebuild the Stride exes after source changes: stale exes were found once and would have produced 60 Hz data.
- Full protocol, one engine variant at a time, strictly sequential: `bash tools/run-all.sh godot|stride|ezengine [--dry-run] [--stages=ABCDEFG]`. `--dry-run` (or `DRY_RUN=1`) prints every command and the planned runtime and runs nothing; do this first.
- Godot: `GODOT_BENCH_EXE=<QuestBench.exe>`, `BENCH_ENGINE=jolt|physx` (default jolt), optional `BENCH_FLAVOUR=<label>` (letters, digits, underscore). Files are named `godot-<engine>[-<flavour>][-stress]-<scenario>-<mode>-<run>`.
- Godot body API: the exe option `--body-api=nodes|rid` (default `nodes`: `RigidBody3D` + `MeshInstance3D` per body). `rid` (RID = resource ID, the opaque handle Godot's servers return) creates bodies and chain joints directly on `PhysicsServer3D` and draws them with MultiMesh. `run-all.sh` takes it from `BODY_API=rid` and shows it in the `--dry-run` command line. Scenario G works with rid too (pieces are server bodies, one MultiMesh). Use a separate flavour so the file names differ from the node runs, for example `BENCH_FLAVOUR=rid BODY_API=rid bash tools/run-all.sh godot`. env.txt records `body_api:`. Results of the A/B: `docs/engine-choice.md` section 12.3.
- Godot rendering driver (Windows): `GODOT_RD_DRIVER=vulkan|d3d12` (optional, needs `BENCH_FLAVOUR`, for example `BENCH_FLAVOUR=d3d12 GODOT_RD_DRIVER=d3d12`) writes `rendering_device/driver.windows` into the `override.cfg` that `run-all.sh` creates; empty keeps the engine default (Vulkan). env.txt records `rendering_driver_setting` and `rendering_driver_in_use`, and the script aborts a cell when they differ. Older results lack these lines; all Godot results so far ran the default Vulkan (`godot/NOTES.md` item 12).
- ezEngine renderer: `EZENGINE_RENDERER=DX11|Vulkan` (default DX11, passed as `-renderer`; env.txt `render_backend` records it). The DX11 against Vulkan A/B is in docs/engine-choice.md section 3.1a.
- Render look (Stride and ezEngine exe option, render mode): `--background=default|cornflower` (Stride default `default` = unchanged behaviour; ezEngine default is `cornflower` since 2026-11-09 and `default` restores the stock clear colour, PROVED by `QbOptions.h` line 36; `cornflower` = Godot's clear colour (0.392, 0.584, 0.929); recorded as env.txt `background:`). For a Godot-like A/B scene test run the same exe with the option off and on and the fitted light: ezEngine `--background=cornflower --sun-intensity=5.8` (default sun 2.0), Stride `--background=cornflower --sun-intensity=0.375` (default 0.55; Stride's default background already is the same blue). The fits (2026-11-09, one scene, one machine) are in SPEC "Settings parity"; the defaults stay so that earlier results remain reproducible. Result of the one-scene A/B (pit-2000, options off against on): no change beyond the run spread, docs/engine-choice.md section 12.5.
- Stride: `STRIDE_BENCH_EXE=<StrideBench.exe>`, `STRIDE_FLAVOR=bepu` (default, JIT) or `bepu_aot`.
- ezEngine: `EZENGINE_BENCH_EXE=<QuestBench.exe>`, optional `BENCH_FLAVOUR`, `EZ_PHYSICS_PATH=components|raw` (default components). Files are named `ezengine-jolt[-<flavour>][-stress]-<scenario>-<mode>-<run>`; the script passes `--project=<abs path of benchmark/ezengine/Project>` itself and aborts when env.txt `physics_space_state_class` is not `ezJoltWorldModule`. No headless mode (physics runs also open a window). `EZ_PHYSICS_PATH` is passed to every cell as `--physics-path`: `components` (default, results label "ezEngine", the engine's Jolt actor components; stepping design in ezengine/NOTES.md) or `raw` (label "ezEngine direct Jolt", bodies through the Jolt BodyInterface; without `BENCH_FLAVOUR` the script sets `direct`, so files are `ezengine-jolt-direct-...`). Unflavoured `ezengine-jolt-...` files written from 2026-11-09 on are components; older sets: unflavoured = raw, `ezengine-jolt-components-...` = components. env.txt `physics_path` proves which. The script aborts when `EXTRA_EXE_ARGS` holds `--physics-path` or when env.txt `physics_path` differs from `EZ_PHYSICS_PATH`. Never mix the two paths in one row. The quick run passes no path, so it runs components. ezEngine exe options beyond the common ones (`--comp-unpaced`, `--count-jolt-steps`, `--chain-sample`, `--phase-timing`, `--raw-update-in-task`, ...) are listed in ezengine/NOTES.md; the diagnostic ones are never used for results. For unpaced ezEngine runs read `steps_per_s_window`, not `steps_per_s` (SPEC "Headline metric"). `BENCH_PROGRESS=1` shows the run progress, `bash tools/bench-progress.sh <OUT_DIR> watch` watches it.
- Other variables: `OUT_DIR`, `WARMUP`, `MEASURE`, `RUNS`; full list in the header of `tools/run-all.sh`.
- Deck-like run (no Deck available): `DECK_LIKE=1` (or `CPU_AFFINITY=<hex mask>`) starts every exe pinned to 8 logical CPUs and caps the engine threads at 8 (Godot worker pool and PhysX workers through `override.cfg`, Stride `--bepu-threads` and `--render-threads`). Tested with a probe exe only: mask 0xFF, arguments and exit code pass through. Use a separate `OUT_DIR`. It only mimics the Deck's thread count; clocks, memory, GPU and Proton differ, so the results are not Deck numbers. Not run yet.
- Progress: `run-all.sh` writes `OUT_DIR/progress-<prefix>.txt` after every cell (cells done / expected cells from the dry-run plan, elapsed, rough ETA, failures). Show it like the build bar with `bash tools/bench-progress.sh <OUT_DIR> watch` in a second shell or as a background task (refresh every 5 s, ends 2 min after "done"; a parent folder such as `.tmp/results-200hz` follows the newest variant). `BENCH_PROGRESS=1` additionally pins the bar on the last line of a real terminal (escape sequences checked with fake cells on a forced 24x80 terminal; not yet watched in a real one). The expected cell count moves with the ladders, so the bar stays below 100% until the run ends.
- Merge: `perl tools/merge-results.pl <results-dir> > SUMMARY.md`.
- Compare two env files key by key: `perl tools/parity_check.pl <a.env.txt> <b.env.txt>`.
- Render sanity check (Stride): `powershell -File stride/render-smoke.ps1 -Exe <StrideBench.exe> [-OutDir .tmp/render-smoke] [-Quick] [-Keep]`. The window must be visible and unobscured.

## Fixed settings (SPEC is the source of truth)
- Physics 200 Hz (dt 0.005 s), max 64 steps per frame, in every scenario, mode and profile. The render loop is unlocked (vsync off, no frame cap), so a frame carries a varying number of steps.
- Profiles: `--profile=game` (default sleeping) and `--profile=stress` (sleeping off); A, D, E, F run in both, B in game only, C and G always use default sleeping.
- Camera: one shared rule from the content bounding sphere (vertical FOV 60, near 0.1, far 2000), see SPEC "Camera".
- Results measured at 60 Hz (older runs, including `results/gdscript-old/`) are NOT comparable with 200 Hz results and must never be merged into one table.

## Gotchas
Each item is stated in the NOTES or SPEC named; PROVED there means measured on one machine.
- The default `--mode` is `physics` and its window draws nothing (PROVED, stride NOTES: black window). Use `--mode=render` to see a scene.
- CLI args need `=`: `--arg=value`. A space-separated form is silently ignored (PROVED, godot NOTES: `--warmup 2` got the defaults).
- Do not combine `--hidden` with Stride physics mode: a hidden window ran about 15 fps (PROVED, 6 s run, cause not investigated). The run scripts do not pass it.
- Godot unpaced runs need a real window (no `--headless`); paced physics runs use `--headless` and ran at about 144 fps there in one smoke (godot NOTES; cause not investigated).
- A PhysX request on a build without the module silently runs GodotPhysics (PROVED, 8 of 8 smoke cells). The engine proof is the class of the direct space state in env.txt (`physics_space_state_class`, `engine_tag`); `run-all.sh` aborts on a mismatch.
- The physx EDITOR exe of the earlier fork build lacked the module; PhysX ran only from the physx template_release exe (PROVED, [godot/PHYSX.md](godot/PHYSX.md)). The clang-built editor was not checked.
- Run on an idle machine with the benchmark windows visible. Other load changed results in several smoke runs (HYPOTHESIS for the cause in each case, stride and godot NOTES).
- One process at a time. Do not run two benchmark runs or builds of the same tree at once.
