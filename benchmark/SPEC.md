# QuestMark engine benchmark: shared specification

Purpose: measure Godot (Jolt) and Stride (Bepu) on the same physics-heavy scenes, so the choice in
`docs/engine-choice.md` rests on data. Both implementations must follow this file exactly; deviations
are recorded in the implementation's own `NOTES.md`.

Targets: Windows build first (dev machine), then the same Windows build on a Steam Deck under Proton.
Baseline numbers from a desktop do not transfer to the Deck. No Deck is available (2026-11-07): the Deck runs are deferred until one is, and every result so far is desktop-only.

## Versions (record the exact ones used in every result)
- Godot: latest stable 4.x with built-in Jolt (`physics/3d/physics_engine = "Jolt Physics"`). Godot may also be tested as a custom-built fork with PhysX (`physics/3d/physics_engine` = `PhysX` | `Jolt Physics`); the engine under test is `BENCH_ENGINE` (`jolt` default, `physx`; GodotPhysics3D is not benchmarked, it is not considered a good physics engine) and an optional build label `BENCH_FLAVOUR` in `tools/run-all.sh`; result files are named `godot-<engine>[-<flavour>][-stress]-<scenario>-<mode>-<run>`, so variants never overwrite each other (jolt without flavour keeps `godot-jolt-`). The engine actually in use is PROVED at run time from the class of `get_world_3d()->get_direct_space_state()` (`JoltPhysicsDirectSpaceState3D`, `GodotPhysXDirectSpaceState3D`, `GodotPhysicsDirectSpaceState3D`), printed at startup and written to env.txt (`physics_space_state_class`, `engine_tag`) and the summary (`backend=`). `run-all.sh` writes an `override.cfg` with `physics/3d/physics_engine` per run and ABORTS when the recorded `engine_tag` differs from `BENCH_ENGINE`: a PhysX request on a build without the module silently runs GodotPhysics (proved). The PhysX fork build is exported with `tools/export-godot-fork.sh` (template and editor paths from env vars, nothing local in the repo). The Jolt limit flags apply to `jolt` only.
- Stride: 4.4.1 (NuGet `Stride.*` 4.4.1) with `Stride.BepuPhysics`. Optional extra run on Stride Bullet. Exe variants: JIT (`dotnet build -c Release`, label `bepu`) and Native AOT (`dotnet publish -c Release -r win-x64 -p:BenchAot=true`, avx2, label `bepu_aot`; `STRIDE_FLAVOR`).
- Jolt limits (Godot): one exe and DLL run both profiles through `--jolt-limits=old|raised` (`run-all.sh` passes it explicitly). Scenarios A, B, C, D and E use `old`: `max_bodies` 10240 / `max_body_pairs` 65536 / `max_contact_constraints` 20480, because the raised pair and constraint caps cost about +20 percent physics tick time in A to D (godot NOTES, A/B). Scenarios F and G use `raised`: 70000 / 1048576 / 1048576. F needs them at large N. G needs them because with the old limits Godot at R=8 printed "contact constraint buffer exceeded, contacts ignored" and at R=32 about 16400 pieces stay alive, above the old `max_bodies` of 10240. Stride (Bepu) has no such limits and gets no flag. The profile in effect is written to env.txt (`jolt_limit_profile_applied_by_extension`, plus `jolt max_*`); `merge-results.pl` shows it per row. Side finding (godot NOTES): raised limits at R=4 printed a "temporary memory allocator exceeded 32 MiB" warning; its cause is a hypothesis, not checked.
- Both: Release / exported build for measured runs; editor or debug runs are not valid results. Godot: release export (Windows Desktop preset, export templates installed). Stride: `dotnet build -c Release`. The Godot benchmark logic (scene building, ray loop, per-tick code, stopwatch, CSV) is a native C++ GDExtension (godot-cpp, template_release, clang-cl /O2 by default; `COMPILER=msvc` is still available; an A/B of both showed no difference beyond the run-to-run spread, godot NOTES), not GDScript; the earlier GDScript version is kept in `godot/legacy/` and its results in `results/gdscript-old/`.

## Common rules
- World: gravity (0, -9.81, 0), fixed physics step 1/200 s (200 Hz, see "Physics rate"), fixed seed `12345` for every random value.
- Units: meters. Bodies: box 0.5 x 0.5 x 0.5, sphere radius 0.25, capsule radius 0.15 height 0.5 including the caps (Godot `CapsuleShape3D.height` 0.5; Stride cylinder length 0.2; both NOTES agree on total 0.5). Mass 1 (density 1000 is not required; mass 1 each). Friction 0.5, restitution 0.1 only where the engine supports it. Known deviation: Bepu (and the Stride plugin) has no restitution, so Stride runs without it (stride NOTES, "Deviations").
- Damping: Godot defaults to linear and angular damping 0.1 (godot NOTES, deviation 9). Both engines use 0.1 and the value is written to env.txt. Stride: the Stride.BepuPhysics 4.4.1 plugin default is 0.05 linear and 0.05 angular (read at run time from `BepuSimulation.PoseLinearDamping` / `PoseAngularDamping`, printed in env.txt as "plugin defaults were"), so the Stride benchmark sets both to 0.1 explicitly (`BenchGame.cs`). Residual difference: the damping formulas of the two engines are not identical (nominal values equal, effect not compared).
- RNG: seed 12345 gives different sequences in Godot and Stride (godot NOTES, deviation 7), so placements, jitter and ray sets differ. The comparison is statistical, not identical layouts.
- Use the engine's default solver iterations; do not tune per engine. Record them. Sleeping follows the profile (see "Profiles"): game = engine default, stress = off for the throughput scenarios.
- Two modes per scenario: `physics` (no rendering, window hidden or minimal, step as fast as the loop allows is NOT used: still fixed 200 Hz, we measure cost per step) and `render` (simple lit meshes for dynamic bodies, one directional light with shadows, 1280x720, vsync OFF, no frame cap; see "Profiles" and "Camera").
- Run length per scenario: 5 s warm-up (not recorded; the warm-up is in seconds of wall time, which at 200 Hz is 1000 steps, the fall of the pit bodies takes about 1.5 s of simulated time so it stays enough), then 20 s measured. Repeat each scenario 3 times, restart the process between repeats.
- Collected every frame (one row per rendered frame, or per step for the unpaced variants), written to CSV `results/<engine>-<backend>-<scenario>-<mode>-<run>.csv`:
  `frame,wall_ms,physics_ms,query_ms,gc0,gc1,gc2,gc_pause_ms,awake_bodies` plus, appended at the END (after the G extras `event_ms,despawn_ms,debris_live`): `steps_per_frame,physics_step_ms` (200 Hz change; the first nine columns keep their order and meaning).
  - `wall_ms`: time between frames.
  - `physics_ms`: own stopwatch in both engines (not an engine counter): time spent in the engine's physics step for the tick (step plus contact/transform sync where measurable), excluding script time in our own per-tick code and the ray batch; 0 on frames without a tick. At 200 Hz a frame carries `steps_per_frame` steps (0, 1, 2, ...: it varies with the frame rate), and `physics_ms` is their SUM: the cost of the physics work of the frame (`physics_frame_ms` in the summaries is the same number). `physics_step_ms` (extra column) is the mean cost of one step of that frame (`physics_ms / steps_per_frame`; Godot also prints a per-step stopwatch statistic). The cost against the 5 ms step budget is `physics_step_ms`; the cost against the frame is `physics_ms`. Summaries also report "tick frames only" stats (use them in render mode). Godot's `Performance.TIME_PHYSICS_PROCESS` is not used: it includes script time and the ray batch and updates about once per second (busy-wait experiment, godot NOTES "Verified" item 4). Godot: time from the end of our last `_physics_process` in a frame to the start of that frame's `_process`, summed over the frame's ticks (covers `end_sync` plus the Jolt step; misses the engine's tick-start state sync). Stride: stopwatch between the Bepu plugin's `SimulationUpdate` and `AfterSimulationUpdate` hooks, summed per Update (Bepu step plus contact flush and transform sync; stride NOTES "How the numbers are taken").
    MISMATCH: the two stopwatches bound different work, so physics_ms is comparable only roughly. Godot includes `end_sync` plus the Jolt step and excludes the engine's tick-start state sync into nodes (about 1 ms in chains, indicative). Stride includes the Bepu Timestep, the plugin's contact-event flush and the transform sync into entities (between `SimulationUpdate` and `AfterSimulationUpdate`) and excludes the plugin's pre-step work before the hook (the previous-velocity update, per PhysicsTimer.cs; other pre-step work not checked).
    Both summaries print "tick frames only" stats (Stride: lines `tick_frames=` and `physics_ms (tick frames only)`; in short Stride physics-mode runs every frame had a tick).
  - `query_ms`: stopwatch around the raycast batch (scenario B only; 0 otherwise).
  - `gc0..gc2, gc_pause_ms`: only for the C# runs (`GC.CollectionCount(n)`, `GC.GetTotalPauseDuration()`), 0 for the Godot C++ extension (native, no GC).
  - `awake_bodies`: number of awake dynamic bodies. Godot: `PHYSICS_3D_ACTIVE_OBJECTS` reads 0 under Jolt in 4.7.2, so it is counted from per-body sleeping state (`PhysicsServer3D.body_get_state(..., BODY_STATE_SLEEPING)`), recomputed on tick frames only. Stride: `Simulation.Bodies.ActiveSet.Count` minus the kinematic ceiling body when it is in the active set (chains, mixed), recomputed every Update.
- Summary printed at exit and written to `<csv>.summary.txt`: median, p95, p99, max of `wall_ms` and `physics_ms`; total GC pause; first 120 frames' max `wall_ms` (first-run hitch).
- Also write `results/<run>.env.txt`: engine version, backend, OS, CPU, GPU, build type, command line. Machine specifics stay in this local file and are never committed.

## Scenario A: `pit-2000` (rigid body throughput)
- Static floor 24 x 1 x 24 centered at y = -0.5 and four static walls 1 thick, 6 high, forming a pit of 22 x 22.
- 2000 dynamic bodies, alternating box and sphere, placed on a 3D grid (spacing 0.6) starting at y = 1, jittered by +-0.05 with the seed, so they fall into the pit together at start. Plain pit-2000 layout rule (both engines): 12 x 12 columns centred on the pit (6.6 m span, inside the 22 m interior), layers 0.6 apart from y = 1, filled layer by layer (x, then z) until 2000 bodies (13 full layers plus 44 bodies of the 14th); body i is a box when i is even, a sphere when odd.
- Neither CCD nor custom shapes; same collision layers for everything.

## Scenario B: `raycast` (query throughput)
- 2000 static shapes (box, capsule, sphere in rotation) at seeded random positions inside a 40 x 20 x 40 volume (y from 0 to 20), random orientations.
- Each PHYSICS STEP (200 per second, not each rendered frame, so the work does not depend on the frame rate) cast N rays closest-hit, from seeded random origins in the same volume to seeded random directions, length 30. Generate the ray set once at start (reuse each frame so the cost is the query, not the RNG).
- Variants: `raycast-1000` and `raycast-10000` (N = 1000 and 10000). Count hits to prevent dead-code elimination and write the total to the summary.
- Raycasts run from the main/game thread in the engine's normal query API (Godot `PhysicsDirectSpaceState3D.intersect_ray`; Stride/Bepu `Simulation.RayCast` via the plugin's API). Note any batching API and do NOT use it unless both engines have an equivalent.

## Scenario C: `chains` (joints and sleeping behaviour)
- 100 chains of 10 capsule links each (1000 bodies, 1000 joints), hung from a static ceiling bar at y = 12, spaced 1.0 apart in a 10 x 10 grid. Link spacing 0.5 vertically. Each chain has 10 joints (ceiling to link 0, then 9 link-link), so 1000 in total; changed from 900 because the top link must be attached for the chain to hang.
- Joint type: ball-socket/pin point joint with no limits (or the closest equivalent available in both engines); note the exact joint type and params in NOTES.md.
- At t = 0 chains hang straight and are pushed sideways by a one-time impulse (2, 0, 0) applied once to the 10th (bottom) link of each chain so they swing (both NOTES agree: Godot `apply_central_impulse` on the first physics tick; Stride once when the body is awake). Chains do not sleep within the 20 s measured window with this setup; record `awake_bodies`.

## Scenario D: `mixed` (everything at once)
- A + B(1000 rays) + C together in one world, A's bodies dropped into a larger pit around the chains. This is the closest to the intended game load and the one to read first.
- Layout rule (Godot implementation, godot NOTES deviation 4): pit interior 32 x 32 (floor 34 x 34); chains as in C; A's 2000 bodies on the 0.6 grid in a ring outside the chains (|x| and |z| within 9 m, excluding |x|<6 and |z|<6), layers from y = 1; 1000 rays cast against the world (A bodies, chains, pit walls); B's 2000 static shapes are NOT added.
  Stride mixed (`BenchGame.cs` `BuildScenario`, `BuildPit(32f, 31, 10, rng)`): pit interior 32 x 32, floor 34 x 34, walls 1 thick 6 high; A bodies on the 0.6 grid, 31 x 31 columns (x, z = idx*0.6, within 9 m), columns with |x|<6 and |z|<6 skipped (tested on the integer index), layers from y = 1 with +-0.05 jitter; chains as in C; 1000 rays; B static shapes not added (summary of a short run: bodies_dynamic=3000, statics=6 = 5 pit + the ceiling). This matches the rule. Remaining differences: the ceiling is a kinematic body in Stride (joint target must be a body; `BenchGame.cs` creates it at y = 12.1, size 11 x 0.2 x 11 per stride NOTES, so the bottom face is at y = 12 as before, changed from 10.5 x 0.1 x 10.5 at y = 12.05 for the shared camera rule) versus Godot's static 11 x 0.2 x 11 slab with its bottom at y = 12. Same size and position, different body type. Ray and jitter sequences differ by RNG (see RNG).

## Scenario E: `unlock` (uncapped frame rate; render mode and physics mode)
- Purpose: how much headroom there is. The physics step stays fixed at 1/200 s of simulated time. Since the render loop is unlocked in every render run now (see "Frame rate"), `unlock-render` no longer differs in loop settings from `mixed` render; what E adds is the same mixed scene reported with fps, the p99 of tick frames and its own file token, and in the physics variant the only place stepping faster than real time is allowed (steps per second = the capacity of the engine, independent of any frame loop).
- Render variant `unlock-render`: vsync off, no frame cap (Godot `Engine.max_fps = 0`; Stride fixed time step off, no target elapsed time), window 1280x720, the same scene as `mixed` (Scenario D). The loop renders as fast as it can while physics ticks every 1/200 s of wall time (200 Hz, see "Physics rate"; the 1/60 s in older notes is the pre-200 Hz state). Report frames per second (frames / measured seconds; with the unlocked loop this is the same as the render `mixed` run, and the number is only comparable on the same machine), `wall_ms` median, p95, p99, max, and the p99 of `wall_ms` on tick frames only.
- Physics variant `unlock-physics`: no rendering, no wall-clock pacing; the physics step runs back to back as fast as possible for 20 s measured (after 5 s warm-up). Report simulated steps per second, `physics_ms` median, p95, p99, max. Use `mixed` and `pit-2000`. This is the only place stepping faster than real time is allowed.
- Each runs 3 times with a process restart, like the other scenarios. CSV columns are unchanged; file names use scenario `unlock-render-mixed`, `unlock-physics-mixed`, `unlock-physics-pit-2000`. The summary adds `fps` or `steps_per_s`.

## Scenario F: `scale` (how many objects fit at the same time)
- Purpose: find the largest number of simultaneous dynamic bodies that still holds the budget. Bodies are the pit bodies of Scenario A (alternating box and sphere, same sizes, mass 1, friction 0.5, damping 0.1), so only the count changes; the pit grows so the layout rule of A holds (12x12 columns centred, 0.6 spacing, layers upward) and the floor and walls scale to keep the bodies inside: pit interior side = max(22, 22 x sqrt(N / 2000) rounded UP to an even number of metres), wall height = max(6, ceil(half the initial column height)) with column height = 1 + layers x 0.6 and layers = ceil(N / 144) (both engines; the rule was equalised when the camera bounds were compared: Godot used a plain ceil and 6 m walls before).
- Ladder of N: 1000, 2000, 4000, 8000, 16000, 32000, 64000. Climb until the first stage that fails the 30 fps limit too (so the maximum N is known for both limits), at 64000 if all pass, or earlier if a stage crashes or runs out of memory (a crashed stage counts as failed; record it). Then run one midpoint stage (rounded to 100) between the last pass and the first fail of each limit (`tools/run-all.sh` scripts this).
- One process per stage, per mode. Per stage: 5 s warm-up, 10 s measured, 1 run for the ladder, then 3 runs of the last passing and the first failing stage.
- Modes: `scale-physics` (200 Hz physics, paced to the wall clock, no rendering, as the `physics` mode) and `scale-render` (200 Hz physics, unlocked render loop, 1280x720, vsync off, lit meshes). Also record the unpaced rate for the same stage in a second pass (`scale-unlock-physics`, as Scenario E physics variant) so the capacity is visible as steps per second.
- CLI (both engines): `--scenario=scale --bodies=N --mode=physics|render [--unpaced=1]`; file tokens `scale-<N>` and `scale-unlock-<N>` (the Godot extension writes the unpaced stage as `scale-<N>-unlock-physics`; `run-all.sh` renames it and `merge-results.pl` accepts both). Unpaced runs need a real window (no `--headless` on Godot).
- Pass criterion per stage (paced modes), PROPOSAL (rewritten for the 200 Hz step and the unlocked loop, see "Frame rate"; the 60 fps frame-count rule no longer applies): real-time factor (RTF = steps run x 0.005 s / measured wall seconds, measured seconds = sum of `wall_ms`) at least 0.99 in every run (the step cost fits the 5 ms budget, no accumulated lag) AND median p99 `wall_ms` at most 20 ms. Also report the 33.3 ms limit separately. Report the maximum N for each limit.
- Record per stage: N, awake bodies at the end, `wall_ms` median, p95, p99, max, `physics_ms` median and p99, process memory at the end (working set), and the paced frame count. The pit settles and sleeping changes the cost, so the warm-up is long enough for the fall (`tools/run-all.sh`: 5 s below N = 4000 on Godot and 16000 on Stride, the lag points seen in the NOTES, measured at 60 Hz and NOT re-measured at 200 Hz (hypothesis: heavy stages now lag earlier, 3.3 times more steps per second), above that `ceil(2 x sqrt(2h/g) + 4)` s with h = N / 144 x 0.6 + 1 m, e.g. 8 s at 4000, 12 s at 16000; the warm-up is wall seconds and the fall time is simulated seconds, so a stage with RTF below 1 simply fails the RTF rule); also report the cost while awake (first 5 measured seconds) separately from the last 5.
- What this does not cover: render-only objects (meshes without physics), draw-call and instancing capacity, scene-tree overhead. These need their own scenario, because the engines render differently (Godot MultiMesh or individual nodes, Stride entities and instancing); they are not part of F.

## Scenario G: `debris` (destruction stress: runtime-created debris)
- Purpose: compare how the engines handle objects that break into many new bodies at runtime, and the cost of creating and removing those bodies. Neither engine has built-in destruction, so the scenario measures the physics-side primitives a destruction system needs: create N rigid bodies with shapes in one frame, give them impulses, let them collide and sleep, remove them later. Fracture geometry is pre-computed (a grid), not simulated.
- World: Scenario A pit floor and walls (22 x 22 interior), plus a fixed set of 25 intact "blocks" (box 2 x 2 x 2, static, 5 x 5 grid, spacing 3, centred) standing on the floor. A block is intact until its event, then replaced.
- Fracture event: remove the block (static body freed or hidden by removal from the simulation) and create 64 debris pieces in the same frame (4 x 4 x 4 grid of boxes of edge 0.5, mass 0.125, same friction 0.5 and damping 0.1), placed where the block was, each with a radial impulse from the block centre (magnitude 1.5 x mass-scaled, plus a seeded +-20 percent factor) and a seeded random spin (uniform in [-3, 3] rad/s per axis). Event timing runs on simulated time (not wall time; simulated time = steps / 200), seed 12345; the lifetime of 8 s is 1600 steps. Debris bodies collide with the floor, walls, remaining blocks and each other.
- Debris lifetime: 8 s of simulated time, then removed. Removal runs in the frame the lifetime ends, for all pieces of an event at once. Debris that sleep stay until removal.
- Event rate (the stress level): R events per second, evenly spaced, drawn from the 25 blocks in a seeded order; block rebuild rule (replaces the literal "rebuilt after its debris is removed", which cannot hold above R of about 3 with 25 blocks and 8 s lifetime): a slot's block is rebuilt when the last live event of that slot is removed; an event on a slot with no block still spawns 64 pieces but removes no block; rebuild time counts in `despawn_ms`. R = 1, 2, 4, 8, 16, 32. Steady-state debris count is R x 64 x 8 (R = 8: 4096 pieces alive, R = 32: 16384; check `debris_live`). Climb as in F (until the first level that fails the 36 ms limit), then one midpoint level (R may be fractional there) between last pass and first fail of each limit. CLI (both engines): `--scenario=debris|debris-pooled --rate=R --mode=physics|render`; file token `debris-<R>` / `debris-pooled-<R>`.
- Modes: `physics` and `render` (200 Hz physics as elsewhere), 5 s warm-up (the debris count reaches steady state after about 8 s, so measure 20 s after a 10 s warm-up here, not 5 s), 3 runs per level for the last passing and the first failing level, 1 run for the others (`tools/run-all.sh` gives R >= 16 one extra rerun slot after a crash or failed sanity check, because those levels lagged in a smoke run).
- Collected per run in addition to the standard columns: `spawn_ms` per event frame (stopwatch around the creation of the 64 pieces plus the removal of the block, written in an extra column `event_ms` appended at the END of the CSV, 0 on frames without an event; the standard 9 columns keep their order), `despawn_ms` per removal frame (extra column `despawn_ms`), and live debris count (extra column `debris_live`). Summary: median, p95, p99, max of `event_ms` over event frames and of `despawn_ms` over removal frames, max `wall_ms` on event frames and on removal frames, the maximum and the mean of `debris_live`, `awake_bodies` min and max, working set at the end, and the number of events completed.
- Pass criterion per level (paced modes), PROPOSAL (see "Frame rate"): p99 `wall_ms` at most 20 ms AND real-time factor at least 0.99 AND p99 `event_ms` at most 8 ms (a single event must not hitch a frame by more than half of a 60 fps frame time). Report the 30 fps variant (p99 wall at most 36 ms) separately. Report the maximum R for each.
- Also report the per-event hitch separately from the steady cost: `wall_ms` p99 on event frames against p99 on non-event frames.
- OPEN ITEM (sleeping): G always runs with the engine default sleeping in both profiles (debris that settle sleep, as in a game); whether G should also have a no-sleep stress variant is not decided.
- Not covered: fracture generation (Voronoi, runtime mesh cutting), per-piece mesh and material creation cost in render mode beyond what the engine does when a body and its mesh are instantiated (record how the render mode creates the meshes: shared mesh resource vs per-piece, same in both engines if possible), object pooling. Pooling is a second variant `debris-pooled` (pre-created pieces reused instead of created and freed) run once per engine at the highest passing R to show how much creation cost matters; it is optional.

## Physics rate
- The fixed physics step is 200 Hz (dt 0.005 s) in every scenario, mode and profile. SPEC is the single source of truth: `physics_hz = 200`. The render loop is not tied to it (see "Frame rate"), so a rendered frame runs 0, 1, 2, ... steps.
- Godot: `physics_ticks_per_second` 200, `max_physics_steps_per_frame` 64 (so no step is dropped above about 3 fps; the engine default 8 would drop steps below 25 fps), `physics_jitter_fix` 0 (not smoothing the step count). Set in `godot/project.godot` and again by the extension at start (`PHYS_HZ`, `MAX_STEPS_PER_FRAME`). Stride: `BepuSimulation.FixedTimeStep` 5 ms and `MaxStepPerFrame` 64. Both record `physics_hz`, `max_physics_steps_per_frame` in env.txt.
- Proof (each run): the summary prints `physics_delta_s` (min and max of the delta seen in `_physics_process`, must be 0.005), `steps_per_s` (about 200 paced), `paced_steps` (steps against 200 x measured s), `real_time_factor` and `dropped_steps_estimate`.
- Unpaced trick (E and the unpaced F stage, Godot): `physics_ticks_per_second` = 200 x K with `time_scale` = K (K = 1000) and `max_physics_steps_per_frame` = 1; the delta given to the step is 1/(200 x K) x K = 0.005 s, proved by the logged `physics_delta_s`. Stride calls `Update(FixedTimeStep)` itself.
- Awake count cadence: recomputed on tick frames only (every frame that ran at least one step). Chain impulse and the ray batch run per step. Sleep thresholds are engine defaults and only recorded (`godot sleep_threshold_*`).
- Effects of 200 Hz: the Jolt substep/iteration settings stay at the engine defaults (recorded), so the cost per simulated second is about 3.3 times that of 60 Hz for the same step cost; the raycast batch (B, D) runs 200 times per simulated second.

## Frame rate (proposal)
- The render loop is unlocked in every run: vsync off, no frame cap (Godot `Engine.max_fps = 0`; Stride `IsFixedTimeStep = false`), in both profiles. Physics stays fixed at 200 Hz of wall time, so steps per frame vary with the frame rate (about 200 / fps); `steps_per_frame` is logged per frame. Physics-mode runs (no rendering): Godot and Stride are both unlocked (Stride `IsFixedTimeStep = false` in physics mode too; proved windowed: 16537 frames in 6 s, `steps_per_s` 199.97). Do not combine Stride physics mode with `--hidden` (a hidden window ran about 15 fps, cause not investigated).
- No step may be dropped: `max_physics_steps_per_frame` is 64; the summary reports `dropped_steps_estimate` (200 Hz x measured s minus steps run; must be about 0 unless the stage lags).
- PROPOSED pass rule for the paced F and G stages (replaces "frames within 1 percent of 60 x s", which cannot hold for an unlocked loop): RTF = simulated s / wall s = steps x 0.005 / sum(`wall_ms`) at least 0.99 in every run, AND the median p99 `wall_ms` within the limit (20 ms, 33.3 ms for F's second limit, 36 ms for G's), AND for G p99 `event_ms` at most 8 ms. `merge-results.pl` and `run-all.sh` implement it; `run-all.sh` sanity checks only reject crashes, early exits and broken pacing: measured wall time below 0.9 x measure s, steps above 1.05 x 200 x measure s, or steps below half of that while no frame hit the 64-step cap (a slow engine hits the cap and loses steps; that is a result, not a crash: Godot Jolt mixed render at about 3 fps and raycast-10000 in every engine, 2026-11-07 run). Not decided: whether 0.99 is the right tolerance; it was chosen to mirror the old 1 percent.
- Prove the loop is unlocked: measured fps above 60 on a light scene (smoke, raycast-1000 render).

## Camera
- Perspective camera, VERTICAL FOV 60 degrees (Godot `keep_aspect = KEEP_HEIGHT`; Stride vertical field of view 60), near 0.1, far 2000, window 1280 x 720, up = +Y, no roll.
- Per scenario compute the content bounding sphere (centre c, radius R) from scene constants AFTER the scenario has set its geometry: c = centre of the content AABB, R = half its diagonal. The camera looks at c from u = normalize(0, 1.5, 0.9) at distance D = 1.15 x R / sin(30 degrees); position = c + u x D.
- Content AABB (union of): every static box (floor, walls, ceiling slab), the spawn volume of the dynamic bodies, the raycast sampling volume, the chains, the debris blocks. Not content: pooled debris parked out of the world, rays. Per scenario (Godot values from env.txt; Stride matches on pit-2000, raycast-1000, chains, mixed, scale-1000, scale-64000, debris-8 after the F pit rule was equalised): pit-2000 R = 17.706; raycast-1000 R = 30.834 (volume (-20.5, -0.5, -20.5) to (20.5, 20.5, 20.5)); chains R = 8.201 (links x, z within +-4.65, y 7.0 to 12.0, plus the slab); mixed R = 24.931; scale-1000 R = 17.328; scale-64000 R = 161.994; debris-8 R = 17.328. Spawn volume of pit bodies: x, z within +-((cols - 1) / 2 x 0.6 + 0.3), y from 0.7 to 1 + (L - 1) x 0.6 + 0.3 (L = layers used).
- env.txt keys (both engines, plain `key: value`): `camera_mode`, `camera_position`, `camera_look_at`, `camera_fov_v_deg`, `camera_near`, `camera_far`, `camera_content_radius`, `camera_content_aabb`.
- `--camera=content|sky` (default content): `sky` keeps the same position and looks straight up (a background-only frame, used to check there is no content in front of the sky).
- Lighting that goes with the camera: ambient light plus ONE directional light (see "Profiles" and "Settings parity").

## Profiles
- `--profile=game|stress` (default game) is a bundle of explicit flags, each settable alone (`--sleeping=default|off`, `--shadows=on|off`, `--shadow-map=<n>`, `--msaa=<n>`, `--vsync=on|off`). Both engines record in env.txt: `profile`, `sleeping`, `shadows`, `shadow_map_size`, `msaa`, `vsync`, `max_fps`, `physics_hz`, `solver_iterations`, `solver_substeps`.
- game: engine default sleeping; one directional light WITH shadows (shadow map 2048, 4 cascades; the engine values in effect are recorded); MSAA 4x; vsync OFF and no frame cap in every run (see "Frame rate", this supersedes the earlier "vsync on for paced runs"); physics rate and solver defaults recorded; default opaque material; bodies cast and receive shadows.
- stress: the same render settings, but sleeping OFF on all dynamic bodies (Godot `can_sleep = false`; Stride: sleeping disabled through the plugin's sleep threshold, see its NOTES), so the pile never sleeps and the cost stays that of an awake pile.
- Scenarios: A (pit-2000), D (mixed), E (unlock) and F (scale) run in both profiles. B (raycast) is identical in both profiles and runs in game only. C (chains) and G (debris) ALWAYS use default sleeping (chains do not sleep in the window anyway; debris pieces that settle sleep as in a game) and run in game only. G is an open item (see G).
- File names: game keeps the plain names; stress adds a `-stress` token after the backend (`godot-jolt-stress-pit-2000-physics-1`). `merge-results.pl` shows Profile and Sleeping columns.
- Smoke proof (pit-2000, physics, Godot, Jolt and PhysX): `awake_bodies` at the end equals the dynamic count (2000) in stress and is lower in game.

## Layout
- `benchmark/godot/`: the Godot project (all measured logic is a C++ GDExtension in `src/`, built with godot-cpp CMake via `tools/build-godot-ext.sh`; performance-critical Godot code is never GDScript).
- `benchmark/stride/`: the Stride solution (C#, .NET 10, scenes built in code, no editor assets).
- `benchmark/tools/`: shared scripts (run all scenarios, merge CSVs into a summary table, parity check, Godot extension and fork export builds).
- `benchmark/results/`: output, meant to be ignored by git (no `benchmark/.gitignore` exists yet; the tree is not a git repo at the time of writing, so add the ignore when it is put under git).
- Scratch files go in `.tmp/` only.
