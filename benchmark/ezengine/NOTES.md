# ezEngine benchmark: notes

C++ ezEngine application `QuestBench` (`ezGameApplication` plus a custom `ezGameState`, `QbGameState`). Physics is the ezEngine Jolt plugin (`ezJoltWorldModule`), the only physics engine of ezEngine, so the result label is `ezengine-jolt`. Rules: `../SPEC.md` (single source of truth). Reference semantics: `../godot/src/quest_bench.cpp` and `../stride/BenchGame.cs`.

Status (2026-11-08): the code compiles in the Dev and Shipping (D3D11) configurations and every scenario ran to exit 0 in smoke form. The Shipping build was timed in the reduced full run of 2026-11-08 (results: docs/engine-choice.md section 12). Nothing in this file is a performance result; the text below was written before that run. Labels: PROVED = checked by a command, file or run; UNVERIFIED = not checked; HYPOTHESIS = a guess that has not been tested.

Naming in the results docs (2026-11-09): the components path (`--physics-path=components`) is called "ezEngine" (default usage) and the raw path (`--physics-path=raw`, alternative; the exe default is components since 2026-11-09) is called "ezEngine direct Jolt" (alternative). Option names are unchanged.

## Files
- `CMakeLists.txt`: the project is built as an external project of an ezEngine checkout (`-DEZ_EXTERNAL_PROJECT_1=<this folder>`, done by `../tools/build-ezengine.sh`). `QB_PROJECT_DIR` (the source path of `Project/`) and `QB_EZ_TAG` are compiled into the exe only; `--project=<folder>` overrides the project folder at run time (needed after a move; `run-all.sh` always passes it, computed from the repo root).
- `src/QbApp.cpp` application and entry point; `QbOptions.*` command line; `QbSetup.cpp` world, Jolt module, render objects, camera, light; `QbScenarios.cpp` scenes A to G; `QbLoop.cpp` the fixed-step loop, per-tick work, render sync; `QbReport.cpp` csv, summary and env.txt in the Godot format.
- `Project/`: the ezEngine project (`ezProject`, `RuntimeConfigs/*`, `Materials/Bench.ezMaterial`). `Project/AssetCache/` and `Project/Editor/` are generated and git-ignored.

## How it works (PROVED by reading and running the code)
- The engine finds `QbGameState` through RTTI: it is the only non-fallback game state of the exe.
- The world is created by the game state with an `ezJoltSettingsComponent` first (the module reads gravity (0, -9.81, 0) and `MaxBodies` once in `Initialize()`), then the Jolt world module. The benchmark pauses the module's own stepping (cvar `Jolt.Simulation.Pause`) and calls `JPH::PhysicsSystem::Update(0.005, 1, tempAlloc, jobSystem)` itself from `ezGameState::BeforeWorldUpdate`, with the engine's own Jolt job system. `physics_ms` is a stopwatch around that call alone (own ray batch, impulses and spawning excluded; the render sync of the transforms is NOT included, it is reported as `render_sync_ms` in render mode). Bodies are created with direct JPH calls (shapes, mass 1, damping 0.1, friction 0.5, restitution 0.1) and registered with the module so that the engine raycast sees them.
- Paced loop: a 200 Hz accumulator with a cap of 64 steps per frame. Unpaced loop (unlock-physics, scale-unlock): back-to-back steps in slices of `--slice-ms` (default 10 ms) and one csv row per step; between slices the engine runs its normal update and message pump. The time spent between slices is printed in the summary (unpaced overhead, window and world update, not part of `physics_ms`).
- Raycasts (scenario B and D) use the engine API `ezPhysicsWorldModuleInterface::Raycast` (closest hit, from the game thread, one ray at a time; no batch API, as SPEC requires). PROVED pitfall: the module drops bodies whose collision group id equals the query's ignore id, and the default ignore id is `ezInvalidIndex`, the id every body without a filter id has, so the default query returned 0 hits on all static shapes. The benchmark passes `ezInvalidIndex - 1` as the ignore id. `ray_api` is recorded in env.txt.
- Chains use `JPH::PointConstraint` (ball-socket without limits) between ceiling and link 0 and between links; joined pairs do not collide (the Godot `PinJoint3D` default), done with per-link filter ids and the module's group filter. The ceiling is a STATIC slab (as in Godot, not kinematic as in Stride). The impulse (2, 0, 0) is applied once to the bottom link of every chain.
- Engine in use is proved at run time: env.txt `physics_space_state_class` holds the RTTI type name of the physics module of the world (`ezJoltWorldModule` in every smoke run); `run-all.sh ezengine` aborts when it differs.
- Jolt limits: A to E use `MaxBodies` 10240 (the old Godot profile has 10240 bodies, 65536 pairs, 20480 contact constraints; ezEngine derives pairs = 40 x and contacts = 4 x MaxBodies, so 409600 and 40960). Scale and debris use `MaxBodies` 70000 (pairs 2.8 M, contacts 280 k; not equal to the Godot raised profile 70000 / 1048576 / 1048576), raised to N + 1000 for larger scale runs. Not tunable separately without patching the engine; `--max-bodies` overrides. The Jolt temporary allocator is the engine's growing allocator (no fixed size, so no 32 MiB overflow like in Godot's old profile); not comparable to the 1024 MiB buffer, recorded in env.txt.
- Sleeping: `--sleeping=off` disables sleeping on all dynamic bodies (`mAllowSleeping = false`), the default keeps Jolt's (sleep velocity threshold 0.03, time 0.5 s, read from the engine).

## Decisions on the open problems
- (a) Headless physics mode: this implementation has no windowless mode (no headless game application was found in the engine source that was read), so physics mode also opens a visible 1280 x 720 window with an empty world and no render objects. UNVERIFIED how much the empty window costs (the engine still updates the world and presents); SPEC says "window hidden or minimal". A hidden or minimised window was not tried.
- (b) Rendering without the editor pipeline: RESOLVED. The engine needs transformed assets (see "Asset transform"). Meshes are created in code (`ezMeshResourceHandle` from procedural geometry) and use `Materials/Bench.ezMaterial`.
- (c) Renderer: the script now configures D3D11 and Vulkan (`EZENGINE_D3D11=0` for Vulkan only); D3D11 was run (PROVED, above). The renderer in use is read at run time and written to env.txt as `render_backend` (`Vulkan` in the first smoke runs, `DX11` in the timed runs; the DX11-against-Vulkan A/B of 2026-11-08 is in docs/engine-choice.md 3.1a) with `render_adapter`. Godot and Stride run on D3D12 / D3D11 / Vulkan according to their own settings, so the backends are NOT the same API.
- (d) MSAA, shadows, light: the atlas 2048, 4 cascades and 4x MSAA are requested through the engine's cvars (`Rendering.Shadows.*`, `Rendering.Pipeline.MSAA`). The values actually in effect for the cascades and MSAA were NOT read back from the pipeline; env.txt says "not read back". The sun is a directional light with the same direction as the Godot scene. The sun and ambient intensities are NOT fitted to the Godot or Stride look: the engine defaults (sun 10, ambient 1) overexposed the stock pipeline (PROVED by screenshot), so the defaults here are sun 2.0 and ambient 0.5, a visual choice by eye on one scene (`--sun-intensity`, `--ambient-intensity`; read back into env.txt). Tonemapping, bloom and ambient occlusion of the stock pipeline are not controlled; the shadow distance is 59 m for the pit (requested and read back). The clear colour is the pipeline default unless `--background=cornflower` is passed (see the section below), not the cornflower blue of Godot and Stride. The render cost of these effects is not equal across the three engines.
- (e) Update and render overlap: ezEngine can run the world update and the rendering of the previous frame in parallel (`Rendering.Multithreading`). It is OFF by default here (`--mt-render=1` turns it on) so that a frame is update then render, as in the other two. `multithreaded_rendering` is written to env.txt. The effect of turning it on was not measured. Frame `wall_ms` therefore includes both, and `render_sync_ms` is the cost of copying body transforms into game objects.

## Render look option `--background=default|cornflower` (2026-11-09, Shipping D3D11, one machine, window captures, not timings)
- `default` (the default, unchanged behaviour): stock pipeline clear colour; corner pixel (2, 14, 25) (PROVED by capture).
- `cornflower`: set in `QbSetup.cpp` (`SetupRenderScene`) through the world blackboard, no engine or project-data edit. Mechanism (PROVED by reading `ezView::RebuildPropertyMappings` and by the capture): a blackboard entry `<pass name>.<property>` overrides a reflected pass property. `ColorSource0..3.ClearColor` is set to the inverse of the stock Hable filmic tonemap (white point 11.2, exposure 1) at the sRGB target (100, 149, 237), because the scene colour is tonemapped before display (a plain linear clear colour gave (45, 75, 125) at the vignetted corner); `TonemapPass.VignettingTexture` is set to `White.color` (the stock vignette darkened the corners). Result: corner pixel (100, 150, 238) to (101, 151, 238) against Godot (100, 149, 237), uniform. Not done: bloom is still on (glow around the bright pit), the dither of about 1 level remains. Assumes camera exposure 1 (the app never changes the camera; `Camera.h` default 1.0, read, not logged at run time).
- A value other than `cornflower` is treated as `default` (no validation). env.txt line `background:` states what was applied.
- Fitted sun for this look: `--sun-intensity=5.8` (default stays 2.0), ambient 0.5 unchanged; see SPEC "Settings parity" (ezEngine table) for the numbers and limits.
- CORRECTED 2026-11-09 (Dev build of the current source, D3D11, pit-2000 render, `-runframes 600 -screenshot`, default and cornflower look): the right interior wall IS drawn; it is lit almost as bright as the floor, so it reads as low contrast against the floor (HYPOTHESIS: light direction against the wall face; not investigated further). The earlier "wall not visible" observation was a misreading of that contrast and is withdrawn. No winding or culling problem was found in these captures (three inner walls and the floor all visible).

## Do the bodies move on screen, and what the port does not test (2026-11-09)
- PROVED (two window captures of the same Dev build, pit-2000 render, DX11, `-runframes 40` and `-runframes 600`, one run each, not timings): at frame 40 the 2000 bodies are still the initial grid, at frame 600 they are scattered over the pit floor with the chains fallen. So the Jolt transforms reach the game objects and the renderer draws the moved bodies (`SyncRender` in `QbLoop.cpp`).
- NOT tested: the engine's own physics components. Bodies are created directly through the Jolt `BodyInterface` (own `CreateBody`, own batched `AddBodiesPrepare`/`AddBodiesFinalize`, own sync of transforms to game objects), only the Jolt module, collision filtering and the world come from the engine. The numbers therefore measure "Jolt inside the ezEngine loop and renderer", not the ezEngine physics integration (actor components, their body creation and transform sync). A variant that uses the components is planned (see "Component variant" below once it exists). The port also uses the STL, not the engine containers; not relevant to the measured paths as far as read (UNVERIFIED).
- `physics_ms` excludes the render sync here, the Godot and Stride numbers include it (see Known deviations); compare frame `wall_ms`, not `physics_ms`, across engines in render mode.

## Known deviations from SPEC and from the other engines
- Dev build in the smoke runs; a Shipping build exists now (above); its window was captured on 2026-11-07 (pit-2000, render, D3D11) and shows the pit with the 2000 bodies, so it does draw. (Timed later, in the 2026-11-08 run.)
- Physics mode opens an empty visible window (a).
- Render path, light and ambient not fitted; renderer is D3D11 in the timed runs (Vulkan in the first smoke runs; A/B in docs/engine-choice.md 3.1a); shadow and MSAA values requested, not read back (c, d).
- Restitution: Jolt supports it (0.1), set on the bodies and the engine default material; the combine rule in the contact listener is friction sqrt(f1 x f2) and restitution max(r1, r2) (as Godot's Jolt). Damping 0.1 on the bodies (Jolt damping; the formula is not compared to Bepu or to the Godot Jolt integration).
- Threads: Jolt runs on the ezEngine task system (env.txt records the short/long worker counts and logical cores); there is no command line flag to set the count, so the `DECK_LIKE` / `CPU_AFFINITY` mask of `run-all.sh` only restricts the process affinity. UNVERIFIED whether the pool shrinks with the mask; the thread count is therefore not enforced equal to Godot or Stride.
- RNG: `ezRandom` seeded with 12345, draw order as in the Godot code, values differ from Godot and Stride, so layouts and ray sets differ in detail.
- Unpaced runs: the loop yields to the engine between 10 ms slices, which adds overhead outside `physics_ms` (printed in the summary). The row per step is timed with one stopwatch around each `Update`.
- Mixed scene: A's bodies in the larger pit around the chains and 1000 rays, B's 2000 static shapes not added, as in the Godot and Stride implementations.
- The first frames contain a large hitch (the window and shader start, about 300 ms seen in smoke runs); the "first 120 frames" statistic shows it, as in the other engines.
- `physics_ms` in render mode excludes the transform sync (above); Godot includes `end_sync`, Stride includes the Bepu transform sync. The stopwatches do not bound the same work.

## Pitfalls found (PROVED, each cost a build or a run)
- `SUPER::BeforeCoreSystemsStartup()` in the `ezGameApplication` subclass resolves to the base of `ezGameApplication`, which skips the unattended-mode setup (the `-runframes`, `-screenshot`, `-logfile` options were silently ignored). The code calls `ezGameApplication::BeforeCoreSystemsStartup()` explicitly.
- Unity build: the entry point macro defines `WinMain`; `<windows.h>` must be included before it in the same translation unit (done at the top of `QbApp.cpp`, which is the first file of the unity unit; error C2731 otherwise).
- `-runframes N -screenshot <png>` writes the screenshot at frame N; the benchmark's own finish must not happen before it (use a longer `--measure`).
- ezEngine fixes the Jolt contact and pair limits by `MaxBodies` (above); a scale run sets `MaxBodies` above N (UNVERIFIED what Jolt does when the limit is exceeded; not tried).

## Component variant `--physics-path=components` (2026-11-09, compiled and run: Dev smoke, Shipping A/B, full A to G run)
- Status (2026-11-09, supersedes the "pit-2000 and scale only" scope of the first version): all stages A to G run with the component path (`BENCH_FLAVOUR=components EXTRA_EXE_ARGS="--physics-path=components --sun-intensity=5.8" bash tools/run-all.sh ezengine --stages=ABCDEFG`). Chains use `ezJoltPointConstraintComponent`, debris pieces are created and pooled as actor components. Full run: 126 cells, 0 failed, 54 min, Shipping D3D11, idle machine, 3 runs per cell in A to E, mostly 1 run per ladder cell (F, G). Results folder (not committed): `.tmp/comp-all5`. That command is the historic one used then (the exe default was raw). Now `EZ_PHYSICS_PATH=components` is the default of `run-all.sh`; the raw path is `EZ_PHYSICS_PATH=raw` (files `ezengine-jolt-direct-...`).
- How the component path is made as fair as the raw path, Godot (nodes and RID) and Stride (all PROVED by reading the code and by the smoke and full runs):
  - The benchmark's own 200 Hz accumulator owes N steps per frame (cap 64, as the other engines). For each owed step the benchmark work runs first (impulses, ray batch, debris spawn: `TickWork`), then one `ezWorld::Update` makes exactly one fixed 1/200 s step (the world clock is set to one step plus 1 ns). The first N-1 updates are made in `RunPaced`, the last one is the application's own update, which also renders. So rays and kicks happen between steps, as in the other engines.
  - Why one step per update: `ezJoltWorldModule::Simulate` merges equal steps into one `PhysicsSystem::Update(N*dt, N)`. Jolt builds the jobs of all N steps up front and the job pool holds 2048 jobs; a step needs at most 7 x workers + 8, so with 8 workers about 31 steps fit. A full pool makes `ezJoltJobSystem::CreateJob` spin forever (the hang seen as 6 timed-out cells in the first full run: scale 4000, debris 8 and 6). Raw does one `Update` per step and has no such limit. With one step per update the hang cannot occur.
  - Debris: a piece created this frame has no body until the next world update, so a flush update without a module step (`FlushNewBodies`) follows the spawn. The linear impulse goes through `AddLinearImpulse` (queued, applied before the next step); the spin is set directly with `SetAngularVelocity` (the component `AddAngularImpulse` is really `AddTorque`: over N merged steps it would give a spin about N x 0.005 too small). Pooled pieces get their kick immediately.
  - Timing: `physics_ms` is the sum of the world update times of the steps of one frame (including the module work outside the Jolt step, and one `RenderWorldDebugInfos` per frame); steps per second are real. `physics_delta_s` and `pacing` are n/a for this path; the impulse probe is reported separately (below).
  - PROVED kick and spin (debris rate 3, 1 run each, the last piece of the first event, same RNG seed): linear speed after the next step 1.7544 m/s (components, created), 1.7581 (components, pooled), 1.7544 (raw); spin set 2.7721 rad/s and read back 2.7721 right after the spawn. The raw spin was not printed. Limits: one piece per run.
- Remaining deviations from the raw path and the other engines (none removed by the fair stepping):
  - Every actor shape is wrapped in a `JPH::StaticCompoundShape` (the capsule has an extra rotated layer); a unique collision group per body and the contact listener are always installed (about +1.7 % of the +5 % pit-2000 gap, PROVED by the A/B below).
  - The chain ceiling has no physics body in this path: the first constraint of a chain is fixed to the world (a point constraint without a parent). Raw and the other engines use a ceiling body. A chain kick response of 0.03 m against 0.10 m was seen in one earlier run; UNVERIFIED whether it persists and its cause is a HYPOTHESIS (compound wrapper, missing ceiling body).
  - The debris pool is parked and woken through the Jolt `BodyInterface` directly (hybrid); the kick uses the component API.
  - The impulse of a piece that has no body yet is deferred to the flush update.
  - Unpaced runs (E and the F unlock cells) use a variable world step of one fixed clock step per update; the module is not given more than one step per update.
  - The raw impulse probe (`|v|` right after the spawn) is not comparable: here the linear impulse is queued (probe reads 0 right after spawn, the speed after the next step is the test).
  - `physics_ms` includes the whole `ezWorld::Update`; Godot and Stride include their transform sync, raw excludes it. Compare `wall_ms` (the unpaced wall ms per step column) across paths.
- Results of the full run (SUPERSEDED for the unpaced E cells by the slice-accounting re-measure below; `.tmp/comp-all5`, Shipping D3D11, game and stress, one machine, idle, batch drift about 5 %; a first full run of the same code on the same machine, whose CSVs were lost, agreed within the drift):
  - A to D paced: real-time factor 1.0 everywhere except raycast-10000 (0.909, query-bound, about 350 ms per frame). Per step on tick frames (game, physics mode): pit-2000 3.07 ms, mixed 2.74 ms, chains 0.56 ms, raycast-1000 0.021 ms.
  - E unpaced (steps per second, physics mode): pit-2000 273.7 (game) / 301.5 (stress), mixed 272.2 / 277.6, i.e. 3.65 / 3.32 and 3.67 / 3.60 wall ms per step. Raw reference (docs/engine-choice.md Table A, 2026-11-07/08 runs): pit-2000 2.54 and mixed 2.13 to 2.23 ms. So the component path is about 30 to 40 % slower than raw on pit-2000 and about 60 to 70 % on mixed in unpaced wall time per step; this is much more than the +5 % found in the interleaved physics-only A/B on pit-2000 below. ### Where the component-path gap comes from (2026-11-09)
- The "+10 %" above was inflated by batch drift: the raw baseline read 3.78 ms in that batch and 3.99 ms in a later one (about 5 % between batches). Only interleaved comparisons count.
- Interleaved decomposition (Shipping, D3D11, pit-2000, render mode, `wall_ms` median, one machine, 20 s measure): raw 3.993 ms; raw plus a unique collision group per body plus a compound shape per body (`--raw-group=1 --raw-compound=1`, emulating the component path inside the raw loop) 4.061 (+1.7 %); components 4.198 (+5.1 %). - Profiler capture of one Dev run (`--profile-dump=1`, Dev build only, writes `profile.json` into `--out`; physics mode, components path, pit-2000, one run including warm-up, Dev timings, profiling overhead included): main thread, per world update, `Wait for Simulate Task` 3.29 ms (waiting for the Jolt step on a worker, `ezJoltWorldModule::Simulate` 3.24 ms), `UpdateDynamicActors` (fetch of the results and transform copy) 0.16 ms. So in this run the module's own work outside the Jolt step is about 0.16 ms per update, which is the size of the remaining gap (PROVED as a measurement of one Dev run; that it fully explains the Shipping gap is a HYPOTHESIS). Raw `physics_ms` excludes the equivalent sync in ezEngine, so it would hide this cost.
